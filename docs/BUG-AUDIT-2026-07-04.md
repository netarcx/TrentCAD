# FrameCAD Bug Audit — 2026-07-04 (fix spec)

**Audience:** the implementing model (Opus). This document is the complete work order: read it top to bottom, then fix the bugs. Every finding below was verified against the actual code by a review agent that read the involved files and their callers; file:line references are against branch `experiment/lore-backend` at commit `1950da1`.

## Ground rules for the fixer

1. **Fix HIGH items first**, then MEDIUM, then LOW. Within a severity, group by file to keep diffs coherent.
2. **Re-verify each finding before changing code** — read the cited lines and confirm the scenario. If a finding turns out to be already handled, skip it and note why.
3. **Do not commit or push without Trent's go-ahead.** When a push does happen, bump the patch/rc digit in `package.json` (both client and `server/` if the server changed) per project convention, and note which side (client rebuild vs server docker rebuild) needs redeploying.
4. Run `npm test` after touching `parts.ts`, `meta.ts`, or `config.ts`. Note: the existing tests mock `persistence`, so the pull-overwrite class of bugs (IPC-1, IPC-2, IPC-3) is NOT covered — add a regression test with a pull mock that rewrites `parts.json`/`parts-meta.json` to a remote snapshot.
5. Some fixes span client + server together (LORE-2, LORE-6) — land both sides in the same change.
6. Follow the repo's terminology discipline (CLAUDE.md): server = team server under `server/`, client = Electron app under `src/`. No git jargon in UI strings.

## Cross-cutting notes

- **DRV-3 (`mapPool`) is a keystone fix**: making `mapPool` drain all workers before rethrowing makes the existing partial-failure manifest-save logic in publish/sync/join sound. Do it first; it shrinks the blast radius of several other scenarios.
- **The "pull overwrites local-only state" pattern** appears three times (IPC-1 for `parts.json`, IPC-2/IPC-3 for `parts-meta.json`, and DRV-1 for CAD files). Fix them with the same philosophy: local unpushed state must never be silently replaced by a remote copy.
- **The Lore backend findings (LORE-1..6)** share one root cause: the team server and `parts.ts` key projects by `driveFolderId`/drive-manifest, and Lore projects don't have one. Consider a shared "backend-agnostic project key" concept rather than six point fixes.

## HIGH severity

### DRV-1 — Sync silently overwrites a user's new (untracked) local file
- **Files:** `src/main/drive.ts:1418-1426` (filter), `1351-1353` (`locallyDirty` build)
- **Problem:** `syncRemoteImpl` protects locally-dirty files from download only when they are already tracked: `if (!isNew && locallyDirty.has(r.relativePath)) return false`. If a file is new on Drive (`isNew === true`, no manifest entry) and the user has an untracked local file at the same relative path (two students both create `Drivetrain/Plate.sldprt`), sync downloads the remote copy and `downloadOne` renames straight over the local file — silent, unrecoverable loss of an unpublished part. Contradicts the function's own contract at lines 1322-1324; the rename-reconcile branch at line 1393 handles this exact case for renamed files, but the plain new-file path doesn't.
- **Fix:** in the `toDownload` filter, also skip when `isNew && locallyDirty.has(r.relativePath)` (local copy wins, matching the modified case), and surface it as a conflict to the user so one copy gets renamed before the next publish.

### DRV-2 — `gcStaging` racing a publish can resurrect promoted staging entries → live published file gets trashed
- **Files:** `src/main/drive.ts:888-905` (gc), `881` (unconditional final save), `1130-1135` (publish's 5s wait cap)
- **Problem:** Publish waits at most 5s (`Promise.race`) for the in-flight stage-chain op, then proceeds with `stagingPaused = true`. `gcStaging` checks `stagingPaused` only at entry; `reconcileStaging` then does one Drive metadata call per stale entry plus a listing sweep (easily >5s) and finishes with an unconditional `saveStagingState(state)` from its **stale** snapshot. Sequence: `open()` fires `void driveGcStaging(dir)` (`drive-project.ts:96`); user publishes; publish fast-path-promotes staged file F for path P and durably deletes P's staging entry (1277-1281); the still-running gc saves stale state, resurrecting `P → F` in `drive-staging.json`. Next reconcile: P is synced (not in `keepRelPaths`), so F — now the live published file — is trashed (line 847). Teammates' next sync deletes their local copies. This is the corruption the comment at 1272-1276 declares impossible. Note `stageFile` re-checks `stagingPaused` after its awaits (line 797); gc has no such re-check.
- **Fix:** re-check `stagingPaused` inside `reconcileStaging` (at minimum right before `saveStagingState`) and abort without saving. Better: re-load staging state from disk before the final save and only remove entries gc itself confirmed trashed, or serialize gc/publish through the same manifest lock instead of the timeout-escapable stage chain.

### DRV-3 — `mapPool` aborts on first error but stragglers keep running and mutate manifest/staging after they were saved
- **Files:** `src/main/drive.ts:105-118` (`mapPool`); consumers at `1183-1269` (publish), `1434-1459` (sync), `519-547` (join)
- **Problem:** `mapPool` is `Promise.all` over workers; on first rejection it rejects while up to 15 other workers **continue transferring**. Callers save the manifest on failure ("persist entries for files that DID upload") while stragglers are still in flight. Consequences: (a) a straggler finishing an upload after `saveManifest` mutates the already-saved in-memory manifest — its entry is lost, the Drive file is orphaned, and next publish `createFileSafe` mints a same-name sibling that flip-flops every client's sync via newest-wins dedupe; (b) a straggler executing the fast-path promote (1194-1220) after publish returns moves the staged file live and trashes the old published id, while the saved manifest still points at the trashed id — user's next publish updates a trashed file teammates never see; (c) in sync, a straggler download landing after the error-path save (1457-1458) leaves an unmanifested file on disk → reads as `added` → next publish re-uploads a teammate's file as a duplicate. `stagingPaused` is also reset (finally, 1310) while promote stragglers still run.
- **Fix:** make `mapPool` wait for ALL workers to settle (collect the first error, rethrow after drain — `allSettled` semantics). No caller changes needed.

### LORE-1 — Part-number coordination entirely bypassed on the Lore backend (duplicate part numbers)
- **Files:** `src/main/parts.ts:538` (`projectKey()`), `parts.ts:579` (`claimNumber` fallback), `src/main/project-backend.ts:96-108`
- **Problem:** `projectKey()` reads `.framecad/drive-manifest.json` for the team-server claim key. Lore projects have no drive-manifest → `null` → `claimNumber()` always falls back to a provisional local number; the server `part-numbers/claim` route is never called and reconcile can never finalize. Additionally the Lore adapter's `pullSharedFile` is a no-op and `pushSharedFile` only stages locally, so the `parts.json` pull/push pattern (`parts.ts:811, 872`) propagates nothing until a full publish+sync. Two students clicking "+ Part" the same day deterministically mint the same `YY-2129-XX-YYY` number.
- **Fix:** make the part-number key backend-agnostic — `parts.ts` should ask `project-backend` for the project key (the `lore://` URL for Lore projects) instead of reading drive-manifest.json directly. That alone restores server-claim uniqueness even with lazy parts.json propagation. Coordinate with LORE-2's server-side key registration.

### LORE-2 — Team server 403s all `:key` routes for students on Lore projects; client then silently skips lock enforcement
- **Files:** `server/src/routes/client.ts:488-496` (`keyAllowed`), `src/main/lore-project.ts:279-284` (`assertLocksHeld`)
- **Problem:** `keyAllowed()` authorizes student access via `SELECT id FROM projects WHERE driveFolderId = ?`. A Lore project's key is its `lore://` URL, which never matches, so for `role === 'student'` every `/api/projects/:key/*` call (locks list, acquire/release, part-number claim, publish history) returns 403 — check-out/check-in buttons error with "You don't have access to this project." Worse, `lore-project.ts` `assertLocksHeld` treats the 403 as "server unreachable" and returns without blocking: the least-privileged users publish with zero lock enforcement while mentors/admins get enforcement.
- **Fix (both sides, same change):** server — register Lore projects with their `lore://` URL as a recognized key (a `loreUrl`/generic `storageKey` column consulted by `keyAllowed`), or key Lore projects by a server-issued id. Client — `assertLocksHeld` must distinguish 403 (surface as an access error, block publish) from network failure (current lenient path). Coordinate with LORE-6.

### IPC-1 — Provisional part-number entries destroyed (and numbers re-issued) by the pull inside create paths
- **Files:** `src/main/parts.ts:811` (`createNewPartImpl`), `905` (`createNewAssemblyImpl`), `507` (`setLegacyMode`); reference merge logic at `parts.ts:660-679` (`reconcilePartNumbers`)
- **Problem:** `pullSharedFile(MANIFEST_FILE)` unconditionally overwrites local `parts.json` with the Drive copy. Entries created while the team server is unreachable are `provisional` and deliberately not pushed (`parts.ts:870`) — they exist only locally. With the server down (routine: self-hosted school server offline, Google fine): "+ Part" → part A gets `26-2129-01-005` provisional/local-only; "+ Part" again → the pull replaces `parts.json` with a remote copy lacking A → `nextCounterFor`/`isNumberTaken` hand part B **the same number and file path**. If A's file was saved, its identity is lost and the next `syncManifest` renumbers it (file named `...-005.sldprt` gets a different number). Also silently drops locally-recorded renames/tombstones (tombstone loss ⇒ number reuse). `reconcilePartNumbers` has re-attach-provisional logic for exactly this hazard, but only runs at open and aborts on first server error.
- **Fix:** after every `pullSharedFile(MANIFEST_FILE)` in a mutator, merge back local-only state the way reconcile does — re-attach `provisional` entries (plus their `assemblies`/counter mappings) and preserve locally-recorded renames/tombstones. Or snapshot the local manifest before the pull and diff-merge instead of accepting the remote wholesale. Apply to all three call sites.

### REND-1 — DetailsPanel wipes unsaved metadata edits whenever the file tree refreshes
- **Files:** `src/renderer/src/components/DetailsPanel.tsx:116-118`; `src/renderer/src/hooks/useGit.ts:35-37,55`
- **Problem:** the meta-load effect is keyed on the `file` **object**, not `file.path`. `useGit` replaces `selectedFile` with a fresh `FileEntry` on every `onFileChange` and every `fetchAll()` (after checkOut/checkIn/sync/publish/create). Each new object re-fires `refreshMeta`, which unconditionally overwrites `mfgNotes`, `mfgMaterial`, `mfgMethod`, `massText`, `costText` with server values. Repro: type manufacturing notes (don't save), click "Check Out" in the same panel — or save the part in SolidWorks so chokidar fires — draft silently discarded. The adjacent where-used effect (138-148) already keys on `filePath` to avoid exactly this.
- **Fix:** key the effect on `file?.path` + `isDirectory` (like where-used), and/or have `refreshMeta` skip overwriting fields the user has dirtied.

### SRV-1 — Unauthenticated CPU-exhaustion DoS: bearer lookup argon2-verifies every device row
- **Files:** `server/src/auth.ts:345-410` (`findDeviceByToken`), called from `requireDevice` (`417-457`)
- **Problem:** token lookup linearly scans every active device and runs `argon2.verify` (default params: m=64MiB, t=3, p=4 — measured ~109ms per verify) on each until match. Any request with `Authorization: Bearer <garbage>` forces a full scan: 30 devices ≈ 3.3s CPU and ~30×64MiB transient allocation, no valid token needed. Authed routes have no IP throttle (only `/api/enroll` and `/api/login` do), and libuv's 4-thread pool means a small flood starves all legitimate auth. Easy OOM/CPU-peg on the documented Raspberry Pi target. The header comment claiming "well under a millisecond worst-case" is off by ~5 orders of magnitude.
- **Fix:** add an indexed non-secret selector so only one row is argon2-verified per request — store a fast lookup key alongside the hash (HMAC/SHA-256 of the token, or a random public token-id prefix minted with the token) and `WHERE lookupKey = ?` first. Needs an additive migration + token-issue path change; existing tokens can keep working via a lazy backfill or one-time fallback scan that writes the lookup key on first successful verify. Also consider lighter hash params for tokens (they're 256-bit random, not passwords) and per-IP throttling on authed routes.

## MEDIUM severity

### DRV-4 — `createFileSafe` retry-lookup keys on bare filename; collides in the flat staging folder → cross-file content corruption
- **Files:** `src/main/drive.ts:202-247` (lookup), `795` (staging passes `relativePath.split('/').pop()!`)
- **Problem:** staged copies live flat in `.framecad-staging/<deviceTag>/` under their basename. Same-basename paths (`AssemA/plate.sldprt`, `AssemB/plate.sldprt`) are normal in CAD. If the first `files.create` for path2 fails transiently, the retry looks up `plate.sldprt`, finds **path1's** staged file, overwrites it with path2's bytes, and returns that id. Both staging entries now point at one fileId with their own hashes; at publish, path1's fast path promotes a file containing path2's content into path1's live location — silent CAD corruption. (Publish-path usage of `createFileSafe` is fine; the bug is specific to staging's flat namespace.)
- **Fix:** give staged files unique names (hash or sanitized full relative path), or thread the intended relative path into `createFileSafe` for staging and verify the found candidate belongs to this entry before updating.

### DRV-5 — Publish swallows transient failures when trashing deleted files; a user's delete silently reverts team-wide
- **Files:** `src/main/drive.ts:1251-1263`
- **Problem:** the deletion worker does a single `files.update({trashed:true})` — no `withRetry` — inside a catch-all that assumes "already removed on Drive", then unconditionally deletes the manifest entry. On any transient error the Drive file stays live, the manifest entry is gone, publish reports success; next sync sees the file as remote-new and re-downloads the deleted file on every client. Contrast `reconcileStaging` (844-854), which distinguishes 404 from transient.
- **Fix:** wrap the trash in `withRetry`; only drop the manifest entry when trash succeeded or the error `isNotFound`; on transient failure keep the entry (retried next publish) and surface it in the result.

### DRV-6 — Google-native files (Docs/Sheets/shortcuts) in the project folder permanently break join and sync
- **Files:** `src/main/drive.ts:459-481` (no mimeType filter beyond folders), `269-274` (`alt=media` download)
- **Problem:** `listAllFilesInner` includes every non-folder item; `alt=media` returns 403 `fileNotDownloadable` for Google-native types. Not 404/auth, so `withRetry` burns 4 attempts (~3.5s) and throws; sync errors on every run (and skips the deletion sweep each time); a fresh join fails partway. One teammate dropping a Google Sheet BOM into the project folder wedges sync for the whole team with an opaque error.
- **Fix:** skip items whose mimeType starts with `application/vnd.google-apps.` in `listAllFilesInner` (resolve shortcuts via `shortcutDetails` or skip them too); log a warning like the unsafe-name path does.

### DRV-7 — Re-joining an existing project silently overwrites unpublished local edits
- **Files:** `src/main/drive-project.ts:163-167`, `src/main/drive.ts:509, 520-524`
- **Problem:** `join` allows re-joining the same project in place ("partial-join repair"), but `downloadProject` starts from `createEmptyManifest` and downloads every remote file over local copies with no dirty check — unlike sync. Re-joining to "reconnect" a project with unpublished changes loses them all, and the fresh manifest discards all change tracking. `downloadProject` also saves the manifest with a bare `saveManifest` outside `withManifestLock` (can race open-triggered gc/metadata manifest writes).
- **Fix:** when a manifest for the same `projectFolderId` already exists at the target, run `getLocalChanges` first and either skip downloads over dirty paths (sync semantics) or require explicit confirmation; take the per-project manifest lock around the manifest write.

### LORE-3 — A failed/interrupted Lore clone permanently bricks the join target
- **Files:** `src/main/lore-project.ts:147-203`
- **Problem:** `writeMeta()` runs only after `cloneRepo()` succeeds. A network drop mid-clone leaves `.lore/` + partial files but no `lore-meta.json`. On retry: same `localPath`, `assertJoinTargetSafe` finds `meta === null`, non-empty check throws "already exists and isn't empty… pick a different save location". The docstring's "partial-clone repair" claim is false in exactly the case that needs it. (Drive avoids this by persisting a partial manifest on transfer failure, `drive.ts:511-547`.)
- **Fix:** write `lore-meta.json` immediately after `assertJoinTargetSafe` and before `cloneRepo`, or have `assertJoinTargetSafe` accept a dir whose `.lore/config.toml` remote matches the join URL.

### LORE-4 — Marker recovery can rebuild the wrong `lore://` key, silently forking the lock/history namespace
- **Files:** `src/main/lore-project.ts:91-126`
- **Problem:** when `lore-meta.json` is missing/corrupt, `open()` recovers the URL from `.lore/config.toml`'s `remote_url`, which (per the code's own comment) may lack the repo-path segment. The recovered value becomes `config.loreUrl` = `projectKey()` — the lock and publish-history key. This client then locks/publishes under `lore://host:port` while teammates use `lore://host:port/repo`: neither side sees the other's check-outs, `assertLocksHeld` passes vacuously — the exact overwrite the lock system exists to prevent, with no error.
- **Fix:** treat the recovered URL as open-only — mark the config so lock/history calls are refused (prompt re-join) until the exact URL is restored, or persist/recover the full repo URL from something Lore itself maintains.

### LORE-5 — Lore publish validates a stale change list, then stages the whole tree
- **Files:** `src/main/lore-project.ts:305-325`, `src/main/lore.ts:331-343` (`rawStageAll` stages `'.'`)
- **Problem:** `publish()` computes `listChanges()`, runs `assertPublishAllowed`/`assertLocksHeld` on that snapshot (lock check includes a network round-trip), then `publishWorkingTree` stages whatever is on disk *now*. A SolidWorks save (or oversized/blocked-extension file) landing in the window is committed+pushed with no size-cap, blocked-extension, or lock check, and is missing from `changedPaths` so history under-reports. (`drive-project.ts:420-440` explicitly closes this hole by running both guards inside `publishChanges` against the exact uploaded set.)
- **Fix:** move the guards inside the serialized unit — in `publishWorkingTree`: stage, re-scan the staged state, run `assertPublishAllowed`/`assertLocksHeld` on that exact set (unstage/abort on violation), then commit+push; record that same set as `changedPaths`.

### IPC-2 — Deferred meta flush swallows push failure; sync then overwrites the unpushed edits with the remote file
- **Files:** `src/main/meta.ts:34-44` (`flushMetaCommit` catch), `src/main/ipc.ts:288`, `src/main/rest.ts:390-393`, `src/main/drive.ts:1418-1426`
- **Problem:** sync flushes the deferred meta commit first specifically so the download can't clobber pending edits — but `flushMetaCommit` catches push failure and returns normally, and sync proceeds. `.framecad/parts-meta.json` can never be in `locallyDirty` (the local walk skips `.framecad/` via `isIgnored`, `drive-manifest.ts:157-175`), so a remotely-changed `parts-meta.json` is downloaded unconditionally. If the push fails while downloads work, the user's last-60s meta edits are reverted; the re-queued retry then pushes the *clobbered* file, finalizing the loss team-wide.
- **Fix:** make `flushMetaCommit` report success/failure; when the flush didn't land, sync must skip downloading `metaRelPath()` (thread a `pendingCommitMessages.length > 0` check into the sync path, mirroring `pullMetaUnlessDirty`), or merge remote+local meta instead of overwriting.

### IPC-3 — `flushMetaCommit` empties `pendingCommitMessages` before the push completes, defeating the dirty guard in-flight
- **Files:** `src/main/meta.ts:29` (`splice(0)`) vs `53-56` (`pullMetaUnlessDirty`)
- **Problem:** the flush splices the queue, then awaits the push (flush is not under `withMetaLock`). A concurrent `modifyAndSync` sees an empty queue → `pullMetaUnlessDirty` proceeds → a pull queues behind the push in the drive-layer queue. If the push fails, the pull downloads the remote copy lacking the just-edited data over the local file; the failure handler re-queues messages after the bytes are gone, and the retry pushes the clobbered file.
- **Fix:** don't clear the queue until the push succeeds (snapshot messages, splice only in the success path, dedupe against messages added meanwhile), and/or run the whole flush inside `withMetaLock` so no mutation interleaves. Fix together with IPC-2.

### IPC-4 — Stale meta-commit state survives project close and contaminates the next project
- **Files:** `src/main/meta.ts:41-44` (failure re-queue + retry timer), `src/main/ipc.ts:465-481` (`close-project`)
- **Problem:** `close-project` awaits `flushMetaCommit`, but on failure messages are re-queued and a 60s retry timer armed — then the project is torn down. The retry later fires against no project (throws, re-arms forever) or against the *next* project. Consequences: (1) non-empty `pendingCommitMessages` makes `pullMetaUnlessDirty` skip the pull-before-modify in the new project, so the first meta edit there works on a stale copy and can overwrite teammates' newer meta on push; (2) the old project's edit is never pushed (silent loss dressed as retry). `open-project`/`drive-join-project` don't flush either.
- **Fix:** on `close-project` (and at the top of open/join), after the final flush attempt, hard-reset the deferred-commit state (clear messages, cancel timer) — or key pending state by project path and drop entries whose project is closed.

### IPC-5 — `handleFileMoves` doesn't retarget drawings' `linkedTo` on rename
- **Files:** `src/main/parts.ts:434-443` vs `781-783` (`renameEntry` does it right)
- **Problem:** when a part is renamed on disk (Explorer / SolidWorks without the add-in) and `syncManifest`'s move detection relocates its entry, drawings pointing at the old path via `linkedTo` are left dangling. Results: `/api/title-block-data` (`rest.ts:557`) falls back to the drawing's own (empty/wrong) meta in title blocks; `check-manifest-integrity` flags the drawing orphaned; the reconcile relabel pass (`parts.ts:718-720`) misses the drawing so a relabelled part's drawing keeps the old number.
- **Fix:** in `handleFileMoves`, after moving an entry `oldPath → currentPath`, run the same `linkedTo` update loop `renameEntry` uses.

### REND-2 — "New Part / Assembly / Folder" buttons double-submit and burn part numbers
- **Files:** `src/renderer/src/components/Toolbar.tsx:83-117, 249-251, 261, 302, 333`; `useGit.ts:207-241`
- **Problem:** the create handlers guard on `isLoading`, but `createNewPart/createSubsystem/createNewAssembly` never set `isLoading` (unlike sync/publish/checkOut), so the guard never engages and the modal stays mounted until the IPC resolves. Double-click or double-Enter fires two `create-new-part` IPCs; main serializes them but creates two parts with sequential numbers — and tombstones make the stray number permanent.
- **Fix:** add a local `creating` busy flag in Toolbar (set before await, cleared in finally) disabling buttons and gating the Enter-key paths, or make the create functions participate in `isLoading`.

### REND-3 — `parseEnrollLink` accepts scheme-less `host:port/enroll/PIN` and yields a broken server URL shown as valid
- **Files:** `src/renderer/src/lib/parseEnrollLink.ts:42-49`
- **Problem:** `new URL('localhost:42130/enroll/ABC234')` parses with protocol `localhost:`, empty host, pathname `42130/enroll/ABC234` — matching `PIN_IN_PATH_REGEX`. Returns `serverUrl: "localhost://"` (verified in Node). TeamEnroll shows the green "Connecting to localhost:// · PIN …" chip; enrollment later fails with an opaque network error. Any pasted link missing `http://` hits this.
- **Fix:** after `new URL()`, require `url.protocol` ∈ {`http:`, `https:`} and non-empty `url.host` before accepting; otherwise fall through to the bare-PIN branch. Consider treating `host:port/enroll/PIN` input as `http://` + input on the fallback path.

### REND-4 — FileThumbnail cache repopulates with stale/cross-project data after project close
- **Files:** `src/renderer/src/components/FileThumbnail.tsx:40-56, 97-99`; paths resolved against current project at `src/main/ipc.ts:623-625`
- **Problem:** `closeProject` calls `clearRendererThumbnailCache()`, but in-flight and queued fetches (`THUMB_MAX_CONCURRENT = 8`; a 500-file project leaves hundreds queued) resolve afterwards and unconditionally `rendererCache.set(key, …)` keyed by `size:<relative-path>`. (1) A project-A request resolving after switching to project B caches A's image under a relative path B also has → B shows A's thumbnail. (2) Queued requests running while no project is open reject → `null` cached permanently → those files never show thumbnails for the rest of the session.
- **Fix:** add a generation counter bumped by `clearRendererThumbnailCache()`; capture at fetch start and skip the `set` when stale; drain `thumbQueue` on clear.

### REND-5 — Sync button double-fires during the pre-sync flush window; no main-process sync mutex
- **Files:** `src/renderer/src/App.tsx:612-615` (`syncWithFlush`), `Toolbar.tsx:126-133`, `src/main/ipc.ts:283-302`
- **Problem:** `syncWithFlush` awaits `parts.flushNow()` (a full `bulkUpdateMeta` round-trip, seconds) before `sync()`, and `isLoading` only turns true inside `sync()` — so the Sync button stays enabled during the flush. A double-click launches a second `syncWithFlush`; the main `sync` handler has no concurrency guard (only publish has `publishingNow`, and even it doesn't reject a second call) and `drive-project.ts sync()` has no internal mutex → two Drive syncs run concurrently against the same files/manifest.
- **Fix:** set the busy state before the flush (or an in-flight flag in `syncWithFlush`), AND add a main-process serialization guard on the `sync` IPC (mirror the REST mutex). Make `publishingNow`-style guards reject/coalesce a second call rather than only flagging.

### SW-1 — Add-in export can silently close a user's open document, discarding unsaved changes
- **Files:** `solidworks-addin/FrameCAD.SolidWorksAddin/SwAddin.cs:662-684, 707-721`
- **Problem:** `ExportSolidWorksFile` decides "already open" solely via `GetOpenDocument(sourceAbsPath)`. If that misses but the doc is open under a different path spelling (mapped/subst drive, symlink — plausible since the path comes from the desktop's project root, not how the user opened it), `OpenDoc6` returns the *existing* document with `swFileLoadWarning_AlreadyOpen` set in `openWarnings`. The code never inspects `openWarnings`, sets `openedByUs = true`, and the `finally` calls `_swApp.CloseDoc(title)` — closing the user's live document without a save prompt.
- **Fix:** after `OpenDoc6`, treat `openWarnings & 128` (`swFileLoadWarning_AlreadyOpen`) as `openedByUs = false`; optionally also compare `doc.GetPathName()` to `sourceAbsPath` (OrdinalIgnoreCase) as a second signal.

### SW-2 — Desktop project switch leaves stale lock state and breaks path translation in the add-in
- **Files:** `solidworks-addin/FrameCAD.SolidWorksAddin/TaskPaneControl.cs:970-976`; `FrameCadApiClient.cs:100-101`
- **Problem:** `CheckConnectionCore` re-runs `UpdateForDocument` only on a false→true `_connected` transition. If the user switches projects in the desktop between two 5s polls, `wasConnected` stays true: the pane keeps showing the old project's lock/checkout state, and `_api._projectRoot` has already been repointed by `GetHealthAsync` — so Check Out/Check In on the still-open old-project doc sends an untranslated absolute path to the REST API.
- **Fix:** when the health poll observes `Project.Path` changed, also re-run `UpdateForDocument(_currentFilePath)` and clear per-file cached state so display and buttons re-derive against the new root.

### SRV-2 — No `trustProxy`: reverse-proxy deployment collapses both brute-force throttles and enables admin lockout
- **Files:** `server/src/index.ts:38-41`; `server/src/routes/public.ts:82, 414`; context at `config.ts:23-25`
- **Problem:** Fastify is created without `trustProxy`, so `req.ip` is the socket peer. The project explicitly steers operators to a reverse proxy for exposure — behind nginx/Caddy every request shares the proxy's IP. The enroll throttle then buckets the whole internet together (20 fumbled PINs from anyone locks out the whole team), and the login throttle key `${ip}|${username}` becomes `${proxyIP}|${username}` for everyone: an attacker who knows an admin username can trip the 5-fail lock and lock out the real admin — the exact DoS the comment at `public.ts:109-115` claims to prevent.
- **Fix:** enable Fastify `trustProxy` behind an env flag (e.g. `TRUST_PROXY=1` documented in `server/.env.example` + README) so direct-LAN deployments don't trust a spoofable `X-Forwarded-For`.

### SRV-3 — Hard-deleting a member cascade-erases their entire publish history
- **Files:** `server/src/db.ts:399` (migration v17: `publish_log.authorId … ON DELETE CASCADE`), triggered by `server/src/routes/admin.ts:450`; `foreign_keys = ON` at `db.ts:513`
- **Problem:** admin "delete member" hard-deletes the row; every publish that member ever recorded is cascade-deleted from every project's history — the product's replacement for git log. `authorName` was denormalized (v17) specifically so history survives renames, but CASCADE deletes the whole row anyway. (`audit_events`, `issue_reports`, `part_numbers` all correctly use `ON DELETE SET NULL`.)
- **Fix:** additive migration changing the FK to `ON DELETE SET NULL` (SQLite: recreate the table or use the rebuild pattern used elsewhere in migrations), or refuse hard-delete when publish rows exist and steer admins to deactivation.
